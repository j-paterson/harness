# Hermes orchestrator

Hermes orchestrator is a local control plane for explicitly assigned coding work. It maintains a private queue, durable project cells, isolated Claude Max profiles, minimal Linear workflow projection, complete lead handoffs, and continuous host-resource observation.

The checked-in policy remains in `observe` mode. Running the CLI does not start Claude, update Linear, stop processes, or remove worktrees unless those actions are separately configured and enabled. Live Phase 2 assembly requires an ignored local policy override plus complete project, profile, and Linear routing configuration; missing or inconsistent inputs fail closed.

## Set up the orchestrator

The project requires Python 3.13 and uv.

```bash
uv sync --python 3.13 --group dev
```

Copy `config/projects.example.yaml` to the ignored `config/projects.yaml` and add only non-secret project routing fields. Keep tokens, account identities, phone numbers, and runtime state outside this repository.

Copy `config/profiles.example.yaml` to the ignored `config/profiles.yaml`. Keep exactly four opaque aliases and point each one at a separate Claude configuration directory. Do not put account email addresses in the aliases, configuration file, or runtime database.

Before a profile can receive work, its scrubbed probe must report `loggedIn=true`, `authMethod=claude.ai`, and `apiProvider=firstParty`. Provider selectors such as Bedrock, AWS, Vertex, Foundry, and Anthropic API-key variables are removed from every Max-profile child process.

Copy `config/linear.example.yaml` to the ignored `config/linear.yaml`. Register only the team IDs and exact state IDs used by projects in `projects.yaml`, plus the operator and QA assignee IDs. The runtime reads the issue first and proves that its Linear team matches the selected project before starting Claude.

The final live switch is an ignored `config/policies.local.yaml` containing `mode: active`. The tracked `config/policies.yaml` stays observation-only, so a fresh clone cannot produce external effects. Active startup runs the ordered cross-system reconciliation to completion first, then probes all four Max profiles and reads the Linear token from macOS Keychain; it does not persist account identity or the token.

Initialize the local database:

```bash
uv run hermes-orchestrator init
```

## Admit explicit work

Add only an issue that the operator explicitly assigned to Hermes:

```bash
uv run hermes-orchestrator queue-add ENG-7 \
  --project PROJECT_ALIAS \
  --priority 2 \
  --operator-instruction CHAT_INSTRUCTION_ID
```

`PROJECT_ALIAS` must exist in `config/projects.yaml`. `CHAT_INSTRUCTION_ID` is the durable idempotency identifier for the operator's instruction; it is required and cannot be reused for different work.

Inspect the queue and state:

```bash
uv run hermes-orchestrator queue-list
uv run hermes-orchestrator status
uv run hermes-orchestrator reconcile
uv run hermes-orchestrator observe
uv run hermes-orchestrator daemon --once
```

`observe` records one resource sample and prints a non-executing plan, even when the local active override exists. Use `observe --watch 60` to continue at an interval of at least five seconds. Resource thresholds begin with conservative hard floors and are refined from real managed work; no waiting period or synthetic load is required. An active daemon starts or resumes Claude only while the resource snapshot is green and startup reconciliation has explicitly opened admission.

Startup reconciliation is one ordered cross-system pass (`Reconciler`): SQLite integrity and incomplete transitions, process leases, worker sessions, worktrees and their remote proofs, the GitHub mutation journal, the CircleCI merge ledger, and the Linear projection, then the admission decision. The pass runs to completion before profile probes and before any scheduling, and it records a structured report of findings in `reconciliation_runs`. The SQLite stage is the first fail-closed gate and a hard abort: when the integrity check or the schema-compatibility check fails, no later stage runs at all — no lease expiry, no worker-lease transition, no custodian call, no git command, and no external read — because durable state that is already known to be unreliable may not authorize any recovery effect. The failed report is persisted from the SQLite evidence alone, the stages list honestly records that nothing after `sqlite` ran, and admission stays closed until the state is repaired. Admission opens only when the report is clean or carries only non-blocking findings; conflicting or unknown evidence — an orphaned or unidentifiable process, a half-finished stop, a missing worktree without a freshly re-proven remote checkpoint, a stored CI failure with no routed correction packet — keeps admission closed with the findings surfaced. The reconciler observes and gates: it never merges, projects Linear, signals a process, or removes a worktree merely to make records agree. Its only effects are the already-journaled recovery paths — registry lease expiry for vanished processes, worker-lease expiry, and custodian worktree convergence, which re-proves the recorded checkpoint on the remote right now and never grandfathers a stale proof.

The live process stage includes a production discovery scan (`ManagedProcessScanner`): a bounded, strictly read-only psutil pass that reports live managed-looking processes not covered by an exact lease. A process is managed-looking only when both markers hold — a managed executable name (`claude`, `codex`, or a Python process running the orchestrator package) and a working directory inside a managed root (a configured project repository or a live worktree lease path) — so ordinary host processes are never reported. Exclusion requires proof: the scanner's own process, an exact `(pid, create_time)` lease match, or membership in a leased process group; unprovable exclusions fail closed and surface as blocking `unknown_live_process` findings that keep admission shut. Attribute reads are defensive, nothing is ever signaled, and a scan that cannot finish inside its bounds blocks admission as `process_scan_unavailable` instead of returning a partial answer.

The external stages hold bounded read-only projection ports in the live runtime. An `attempted` GitHub merge effect is projected against the exact recorded repository, pull-request number, and head SHA: a pull request merged at exactly the reviewed head resolves as a non-blocking finding (the durable `attempted` fence stays in place forever, so a duplicate merge remains impossible), while an open pull request, a merged head that is not the reviewed head, or an unavailable read each block admission. A pending Linear effect is projected against the exact journaled target using the configured team, state, and assignee identities: a target that already holds resolves, an issue provably unchanged since the journaled read is reported as a safe pre-mutation crash, and a team mismatch, a changed-but-unmet issue, or an unavailable read each block. The CI stage projects recorded merges for `ci: circleci` projects onto their known CI outcome by exact identity — a mismatched or unavailable known state blocks — while `ci: none` projects stay informational with zero CI calls. The ports only read; they never merge, never mutate Linear, and never resolve anything that is not proven by exact identities. Observation mode and tests run without ports, where every pending external row simply stays blocking.

Hermes can use the same strict JSON boundary as the future phone console:

```bash
uv run hermes-orchestrator hermes-command --json \
  '{"intent":"queue_issue","issue_id":"ENG-7","project_key":"PROJECT_ALIAS","priority":2,"operator_instruction_id":"CHAT_INSTRUCTION_ID"}'
```

The boundary accepts only `queue_issue`, `status`, `pause`, `resume`, `retry`, `reprioritize`, `approve_handoff`, `qa_reject`, `pending_corrections`, `ack_correction`, `pending_wakes`, and `ack_wake`. It has no command for discovering or claiming Linear work.

A lead turn's terminal boundary — completed, provider capped, blocked, or handoff required — commits exactly one deduplicated, metadata-only wake row. When `config/hermes.yaml` supplies a `wake_command`, the daemon pushes each committed wake directly to that consumer command with the wake's JSON on stdin and `wake_id` as the idempotency key, acknowledging the row only after the command exits zero; a rejecting, failing, or hanging consumer leaves the row pending and the supervisor interval is the retry backoff. `pending_wakes`/`ack_wake` remain the operational fallback surface — Hermes never polls lead progress. Every terminal boundary — including a turn that finds its issue already completed — journals identity-complete durable evidence at the transition, and daemon startup deterministically reconstructs any wake lost between that evidence and the outbox insert into the same deduplicated identity, bounded by a migration-recorded floor so upgraded databases never manufacture historical wakes.

## cmux terminal visibility

With `config/cmux.yaml` present (see `config/cmux.example.yaml`), the daemon binds each orchestration seat — the Hermes `Orchestrator` pane and one workspace per active Claude project lead — to exact cmux workspace/surface UUIDs in durable state (`cmux_surface_bindings` and `cmux_activation_intents`, migrations 0025–0027). Visibility is strictly observational: the adapter speaks only an allow-list of metadata commands (workspace lifecycle, status, progress, notifications, focus), never `read-screen`, `capture-pane`, or `send`, so screen content structurally cannot advance issue state; durable SQLite/event state stays authoritative. Every seat transition journals a replay-safe `cmux_binding.*` lifecycle event and ownership never transfers silently: startup reconciliation validates the exact recorded UUIDs, replaces a missing lead surface with one new generation rebuilt from durable identity alone (recorded project cwd, the profile's exact `CLAUDE_CONFIG_DIR`, and a sanitized `claude --resume <session>` native resume command — never a prompt or credential), records a seat whose profile or project no longer resolves as lost instead of adopting a substitute, and rebinds a missing Orchestrator seat only to the daemon's own cmux-injected seat. Seat lifecycle is write-ahead and compensated so no live workspace can fall outside durable ownership: before the external create runs, a `cmux_activation_intents` row commits a durable unique operation identity that travels inside the requested workspace title, so even a crash after cmux creates the workspace but before its returned UUIDs are persisted leaves the exact workspace correlatable to that intent (reconciliation reclaims it only when exactly one live workspace carries the marker as an exact whitespace-delimited token, aborts an intent no live workspace carries, and fails closed on duplicated markers — closing nothing, keeping the intent pending and hibernation blocked, and reporting the pass ambiguous/incomplete for operator resolution — never adopting an unrelated workspace by cwd, title heuristics, or substring look-alikes). Once cmux returns, the identities bind atomically to the intent as a `residual` row and are promoted to the active seat in the same transaction that retires the generation it replaces, so neither an insert failure nor a crash between phases can leave a terminal old generation without a successor or an untracked workspace; after promotion the cosmetic marker is renamed out of the visible title. On session rotation the old workspace is closed by exact UUID before its binding retires; an activation that cannot finish is closed immediately or left as its `residual` row — durable ownership evidence that blocks hibernation until it is reclaimed (closed, or recorded lost if the workspace vanished). A cell with an unresolved residual or pending activation intent is refused a replacement seat: dispatch first resolves the evidence by exact identity (startup reconciliation does the same), so one cell can never operate two live workspaces, and a pending intent blocks hibernation exactly like a residual. Reconciliation is itself an optional boundary: a cmux denial, timeout, or protocol failure after the initial ping ends the pass with a partial report, leaves every unfinished binding recoverable, and never prevents the daemon from starting. Status updates are event-driven off the durable wake outbox — the pane never wakes a model on a timer. cmux hibernation is enabled only when every bound lead is simultaneously idle (no live process lease), restorable (active cell), and checkpoint-safe for its exact session; any running or uncheckpointed lead blocks it. Socket auth: a process launched inside a cmux pane is authorized by cmux itself; the daemon and every other outside process read the optional password from the Keychain service `hermes-orchestrator-cmux` at call time and passes it exclusively through the `CMUX_SOCKET_PASSWORD` environment variable — it never appears in argv, config, logs, events, or exceptions, and denial fails closed without touching the bindings. `hermes-orchestrator cmux-focus [--project <key>]` focuses the bound surface from durable project/cell metadata. The Orchestrator workspace itself is owned autonomously (INFRA-191): the ONE production daemon runs OUTSIDE cmux (launchd) holding the exclusive state-directory fence (`<state-dir>/daemon.lock`), and its lifecycle owner creates/adopts/recovers one two-pane `Orchestrator` workspace — the upper pane runs the lock-free, token-free, read-only `hermes-orchestrator dashboard` entry (one `mode=ro` SQLite connection for both the schema check and all reads; it refuses on any migration-generation mismatch and never mutates daemon state), and the lower pane runs the installed Nous Hermes classic durable session (`hermes chat --continue <name> --create-if-missing`). Never run `hermes-orchestrator daemon` inside a cmux pane: a second daemon against the same state directory loses the exclusive fence and exits. Both panes are role-proven from typed metadata only — the cmux process tree's names/PIDs correlated with `ps` argv strictly through those PIDs and their descendants — and every workspace-mutating entry (the daemon's owner and manual `orchestrator-workspace ensure|smoke`) serializes through that same fence: the manual CLI acquires it non-blocking and refuses cleanly, with zero binding/cmux effects, while the daemon owns it; a smoke against an isolated `--state-dir` takes that directory's own fence and stays permitted. Each confirmed lead session receives its own workspace showing the current issue id.

For Hermes chat intake, trust this repository once with:

```bash
hermes skills trust /PATH/TO/hermes-orchestrator
```

New Hermes sessions started inside the trusted repository can load the repo-local `hermes-orchestrator-intake` skill. The skill reads only the explicitly supplied issue through the official Linear MCP, routes Infrastructure issues to the `agent-orchestration` project, submits the strict `queue_issue` command, and verifies the private queue read-back. It does not replace or wrap Hermes's direct Linear MCP access.

Linear status keys in `config/linear.yaml` are logical orchestrator milestones. A team may map `In Development` and `Review` to differently named workflow states such as Infrastructure's `In Progress` and `In Review`. `QA` may be omitted for teams without a QA state; requesting a QA projection on such a route fails closed.

QA routing is explicit and durable. `queue_issue` accepts an optional `qa_origin` of `ordinary` (default), `ryan_assigned`, or `operator_designated`; it is recorded at admission and never inferred from later assignment changes. After the Codex Merger's proven merge, ordinary work projects `Done` to the operator, operator-designated work projects `QA` to the operator, and work Ryan assigned from QA returns to Ryan in `QA`. A QA rejection supersedes the merged review, projects `In Development` to the operator, and returns a Critical correction packet to the Claude lead; the corrected work returns to Ryan in QA again after its next merge. Every merge path before ancestry proof leaves Linear in `Review`, and the merged item is journaled in the CircleCI window without any CI query.

The Codex merge flow is event-driven end to end. At a freeze boundary the lead runs `hermes-orchestrator candidate-ready ISSUE --project ALIAS --verified "uv run pytest -q=N passed"`, which proves the clean, pushed feature-branch head, publishes an immutable manifest under the state directory, registers the wake durably, and queues the typed `FABLE_READY` envelope onto the project's Merger thread through `codex queue`. When the Merger's turn completes, the daemon's App Server listener (or `hermes-orchestrator merger-turn --project ALIAS`) admits the delivered wake through the CircleCI reconciliation and one-open-pull-request gates, reads the thread's structured report, and drives the review service: correction packets land in the durable `lead_corrections` outbox (`pending_corrections` / `ack_correction` intents) for Hermes to return to the exact lead, approved candidates merge only through the GitHub adapter with ancestry proof, and the merged item is journaled unresolved until the next candidate boundary reconciles it. A full merge window marks the wake `deferred`; the candidate is re-emitted as a new event once a prior pipeline resolves. A prior CircleCI failure blocks every intake until an explicitly bound rework arrives: the lead emits `candidate-ready ... --status FABLE_REWORK_READY` for the failed issue on its branch, the intake gate admits it only because the durable `ci_failure` correction packet for that exact reviewed SHA authorizes it, and the failed ledger row transitions to `corrected` (recording the rework event, SHA, and correction id) only after full admission; ordinary, stale, foreign, or rejected candidates never change the failed state and replays are idempotent. A newly created Merger task is `notLoaded` until it is opened once in Codex; a queued wake is held until then and the completed turn settles it — `candidate-ready` reports `awaiting_load`, and nothing polls or re-wakes. Persisted tasks are re-verified by `thread/read` alone; `thread/resume` is attempted only for `notLoaded` tasks and a rejected resume never marks a still-readable channel uncertain. `qa_reject` returns merged QA work to the lead with a Critical packet.

Legacy durable databases whose migration 3 predates reviewer channels are upgraded forward-only by migration 9: `reviewer_channels` is created if missing, any legacy `merger_threads` row is carried over as a `configuring` channel that becomes ready only after live re-verification, and already-applied migrations are never edited or re-run. GitHub and CircleCI tokens are read from Keychain services `hermes-orchestrator-github` and `hermes-orchestrator-circleci` (account `default`).

Each project declares an explicit CI policy in `projects.yaml`: `ci: circleci` (the default) reconciles merged candidates against CircleCI at intake boundaries and keeps every non-success — including a 404 for a repository that is not configured in CircleCI — ambiguous and fail-closed; `ci: none` declares that the repository has no CI, so merged items resolve durably as `ci_not_configured` with zero CircleCI calls and never permanently consume the merge window. No-CI is never inferred from a CI response. The `hermes-orchestrator-circleci` Keychain token is required only when at least one configured project uses CircleCI.

The Linear token is read at runtime from macOS Keychain service `hermes-orchestrator-linear`, account `default`. Linear projections read the issue first and can change only the approved state and assignee fields. Team validation happens before Claude starts, and reconciliation can veto every otherwise executable dispatch.

Every managed process — Claude lead turns, the Codex App Server, and `codex queue` invocations — is registered in `process_leases` immediately after it is spawned in its own session, recording pid, process group, executable, working directory, project, worker, and psutil `create_time`. A child that cannot be registered is terminated and its launch fails closed. Stops require a checkpoint id, re-validate the recorded identity before any signal (a reused PID is never signaled), SIGTERM the exact recorded group, wait the bounded grace period, and SIGKILL only the same validated group; every signal and result is journaled. Reconciliation expires leases whose process is gone and reports live orphans as findings that keep admission closed. Nothing is ever killed by name or path. A stop is a durable, owned claim: the checkpoint, owner token, phase, and claim expiry are journaled before any signal, exactly one caller may advance each phase (`term_claimed` → `term_sent` → `kill_claimed` → `kill_sent`), identity is re-validated immediately before each signal, and a stale claim is recovered only after its lease expires without re-sending a possibly-sent signal. `candidate-ready` runs the durable intake gate before queuing the wake, so a deferred or blocked candidate never wakes the Merger; the turn-time gate replays that event-bound decision with zero CI calls.

Admission is governed by the calibrated thresholds in `config/policies.yaml` (`resource_thresholds`): green admits work; yellow — any yellow floor, swap growth above `yellow_swap_growth_gib_per_hour`, sustained load above `yellow_load_ratio`, or macOS memory-pressure warning — closes admission for priority 2–4 work while priority 1 and all active work continue; red — any red floor or critical memory pressure — additionally requests exactly one checkpoint per tick from the lowest-priority checkpoint-safe lead (ordered by priority, dependency criticality, recent progress, then RSS), re-sampling before any further request. Levels worsen immediately and relax only after `hysteresis_samples` consecutive calmer samples, so green and yellow never flap. Uncalibrated thresholds keep admission closed. Nothing here terminates a process. A red checkpoint targets only a lead with current durable safe-boundary evidence (`checkpoint_safety`, recorded when its turn completes normally, bound to its exact session, and invalidated the moment new work is dispatched, the session rotates, or the start fails); missing, stale, or prior-session evidence is unsafe, so admission closes but nothing is requested. Checkpoint requests are durable (`checkpoint_requests`) with an idempotent identity per proven boundary; exactly one may be pending host-wide, new requests are suppressed while one is pending or until a fresh red sample follows its completion/failure/stale transition, and the rule is reconstructed from the database after a restart. Delivery is a separate durable step: the supervisor delivers each reserved request through a dispatcher that revalidates the exact cell and session at execution time and records `delivered_at`; a missing callback, a session/target mismatch, a cell that is no longer active, cancellation, or any exception transitions that exact request to `failed`/`stale` with bounded evidence before the error propagates, and a request reserved just before a restart is delivered exactly once on the next tick.

Leads rotate at the approved context and active-time boundaries. Active execution time is tracked per lead session as durable intervals (`active_intervals`) — idle time between turns never counts — and context evidence (`context_evidence`) aggregates the context percentage derived from the latest top-level usage against `context_window_tokens`, compaction events, rapid refill after compaction, explicit context-window errors, and behavioural warnings into one sticky per-session decision: `prepare` (at `context_prepare_percent` or a first compaction) requests a handoff draft without stopping assigned work; `rotation_pending` (at `context_rotate_percent`, repeated compaction with rapid refill, or `max_active_session_hours` of active time) stops new subwork and waits for a completed turn as the safe boundary; `rotate_now` invokes the existing acknowledged handoff flow. A behavioural warning alone can never force rotation, and a context error is an emergency that requires the handoff immediately. `rotation_pending` is an operational freeze, not just a recorded state: the lead runs with a Claude Code `PreToolUse` hook on the `Agent` tool (`hermes-orchestrator subagent-gate`) that blocks new subagent assignments while a durable per-session freeze marker exists, the orchestrator writes that marker the moment the threshold is crossed (before any worker lease can be created) and refuses to lease any `subagent.started` observed afterwards, existing work still runs to its safe boundary, and the marker is removed when the session rotates. The marker is reconciled idempotently from durable context state every time a session is started or resumed — before the lead can emit an event or admit an `Agent` call — so a process that stops between the durable transition and the marker write can never leave a frozen session operationally unfrozen; reconciliation journals `assignments.frozen` only when it actually writes a marker and never duplicates transition events or handoff requests.

Stalls are diagnosed only from corroborated evidence — elapsed time alone never counts — and normalized to a closed set of reasons (`provider_limit`, `authentication`, `approval_wait`, `dependency`, `merge_conflict`, `ci_failure`, `environment_failure`, `resource_pressure`, `repeated_command_failure`, `agent_uncertainty`) paired with an exact evidence predicate. Hermes reports evidence with `report_stall`; the orchestrator asks the operator on the first two occurrences of a predicate (`pending_consultations`), and `approve_playbook` writes the approved remedy — actions, verification, timeout, rollback, optional project override — atomically to the versioned `config/playbooks.yaml` and records its content hash in SQLite. Only the third exact recurrence runs automatically, and only when two approved consultations bind the same predicate and exact playbook entry, the file is an operator-written version, and no automatic remedy has failed or timed out since (`record_remedy_result`). Credentials, spending, external messages, destructive exceptions, and unregistered commands always ask the operator. A stall is never diagnosed from elapsed time alone: inactivity counts only when the process is dead or shows neither output nor resource activity, so a quiet but CPU-active test or build is a long-running command, not a stall. On the exact third recurrence the approved remedy is actually applied by a fail-closed executor: only registered actions with a wired handler run, the whole remedy plus its named verification must finish within the approved timeout, the approved rollback runs on any failure, and the outcome is recorded durably — a failure, timeout, or failed verification returns the next recurrence to the operator. Remedy handlers, verifiers, and rollbacks are async-only and cooperatively cancellable: a synchronous callable is refused before any action starts (recorded as a failed execution that revokes automation), one deadline spans the actions and the verification, on timeout the running coroutine is cancelled and its cancellation awaited before the approved rollback runs so a timed-out action can never apply a late mutation, and rollback is bounded by the same approved timeout with its own timeout or failure recorded. Everything runs on the event-loop thread that owns the single SQLite connection; SQLite's same-thread guard stays on. The wired `wait_for_reset` remedy schedules durable, restart-safe work (`scheduled_resets`) that the supervisor consumes once due, and `pause_issue` acts only on exactly one in-flight issue for the project — a missing or ambiguous target fails closed — and verifies that exact issue.

## Classic in-pane leads and the lead-intake transport

With cmux configured, lead seats are classic by default (`classic_leads` in `config/cmux.yaml`): the visible seat activates **before** any lead process exists, and a failed or unresolvable activation refuses the launch entirely — a lead without its seat would be a hidden process, so nothing is launched and there is nothing to compensate. The seat's workspace runs the sanitized native interactive Claude TUI command for the exact session (`claude --resume <id>` / `claude --session-id <id>`, validated by grammar — never a prompt, flag, or credential) under the leased profile's exact `CLAUDE_CONFIG_DIR`; the daemon launches no `-p`/stream-JSON shadow of it, records durable classic-seat evidence (`cmux_classic_seats`, migration 0028), and refuses the seat before creation unless the profile's read-only `claude auth status` probe proves a logged-in first-party Max account (the probe can never start an OAuth flow). cmux 0.64.x's short mutation acknowledgement (`OK workspace:<n>`) is accepted only as an intermediate response and resolved to exactly one workspace UUID through the metadata listing and the durable activation-intent marker — zero or multiple exact matches fail closed, and adoption by cwd, generic title, list position, substring, or focus is structurally impossible.

Hermes hands work to a classic lead through a bounded signal plane with SQLite as the authoritative data plane (`lead_intake.py`). The primary wake for an already-idle classic session is one `cmux send` operation to the exact validated workspace and surface, whose sole permitted content is the closed signal grammar — `HERMES_CORRECTION_READY <id>` or `HERMES_WORK_READY <id>` plus one trailing newline that submits the envelope and Return together (operator-approved 2026-08-29); the full-match grammar refuses payload text, extra tokens, malformed ids, embedded newlines, whitespace, and shell syntax before any subprocess exists, and raw `send`/`send-key` stay structurally rejected everywhere else, so nothing outside the grammar can ever reach a terminal. The packet itself never rides cmux: the signalled lead retrieves it from durable SQLite by its id, verifies project/issue/session, and acknowledges through the existing intake and correction APIs — terminal text is never authoritative, and a delivered or acknowledged id is a no-op. Delivery runs the durable claimed/attempted/announced state machine per (kind, packet, session) in `lead_intake_deliveries`: rowcount-checked compare-and-swap claims before any external effect, windowed retries of uncertain attempts, derivation from durable state on every startup and maintenance tick (a crash can never permanently separate publication from its signal), supplemental `set-status`/`notify` metadata that is never treated as delivery, and containment of every refusal and cmux failure with the durable packet retained. The Stop-hook `intake-poll`/`intake-ack` offer lease remains the turn-boundary fallback drain: the poll leases one envelope as an offer under an opaque token, only the lead's explicit CAS-bound acknowledgement records delivered, unacknowledged offers re-offer under fresh tokens after expiry, and stale, foreign-session, wrong-packet, duplicate, or superseded acknowledgements are rejected without effect.

Install the fallback poll on a classic lead by adding a Stop hook to the profile or project Claude Code settings. Derive the deployed paths instead of assuming a checkout — the project root is wherever the orchestrator repository actually lives on the host, and the state directory is the configured `--state-dir` (default `~/.local/share/hermes-orchestrator`):

```json
{"hooks": {"Stop": [{"hooks": [{"type": "command", "command": "uv run --project <deployed-hermes-checkout> hermes-orchestrator --state-dir <deployed-state-dir> intake-poll"}]}]}}
```

Validate an installation by running the exact hook command once with `--session <session-id>`: it must resolve the deployed binary and open the live state database, returning either one offer or nothing. The hook receives the session id on stdin, returns at most one offer as hook JSON, and is a silent no-op when nothing is pending.

## Migration-heavy work: disposable environment and pre-candidate gate

`hermes-orchestrator migration-env` provisions and proves the local-only completion environment migration- or generation-heavy lead work must pass before claiming a merge-ready boundary. `provision --execute` starts one dedicated disposable PostgreSQL container that publishes only `127.0.0.1:<port>` and idempotently creates a source/target database pair named under the target repository's guarded `jo_local_*` convention with an explicit disposable infix (`jo_local_fable_<slug>_{source,target}`); the tooling structurally refuses every other name and every non-loopback host, so shared dev, preview, staging, neon, and production databases are out of reach by construction. `mark` stamps an isolated worktree with a marker file, and `gate --execute` refuses any checkout without it, so the operator's primary checkout cannot be mutated. The gate is one deterministic ordered pass that fails closed: loopback-binding proof, guarded-naming proof, the exact pending-migration set before and after `prisma migrate deploy`, a second deploy proving idempotence, the synthetic (faker-seeded) corpus plus eligibility-key hydration, the repository's historical LoanConfig/LoanProductConfig data migrations (dry-run before apply), schema authority via a `prisma migrate diff` shadowed by the disposable source database, and two generator passes whose output trees must be byte-identical. The first failure marks every remaining check `skipped` and the verdict red; exceptions surface as type names only; the verdict persists as durable JSON keyed to the exact repository head, and connection strings never appear in argv output, verdicts, or the handoff. Target-repository commands are `pnpm --filter @jo/database` package scripts exclusively — never the repository-root wrappers, which load dotenv files and chain a staging WorkOS reset. `handoff --out` renders the durable local handoff: exact commands, environment variable names only, safety assertions, and the recorded remote-only limitations (the stage restore behind `DATABASE_URL_READ_ONLY_STAGE`; production dumps are customer data and never enter this environment). While any applicable check is red or unproven, migration-heavy work must not claim a merge-ready boundary.
